# Day 07 – Linux File System Hierarchy & Scenario-Based Practice

## Part 1: Linux File System Hierarchy

### Core Directories (Must Know)

#### 1. `/` (root)
* **What it contains:** The top-level directory. The absolute starting point of the entire Linux directory tree. All other directories branch out from here.
* **Example files/folders:** `bin`, `boot`, `dev`, `etc`, `home`, `lib`, `root`, `usr`, `var`.
* **I would use this when:** I need to navigate to the very absolute beginning of the system or reference absolute file paths.

#### 2. `/home`
* **What it contains:** The personal directories (home folders) for standard, non-root users to store their private documents, settings, and code.
* **Example files/folders:** `/home/ubuntu`, `/home/developer`, `.bashrc`, `.ssh`.
* **I would use this when:** I am logged in as a normal user and want to create, edit, or download my personal project files and scripts.

#### 3. `/root`
* **What it contains:** The dedicated, separate home directory exclusively for the superuser (root). It is not inside `/home`.
* **Example files/folders:** `.bash_history`, `.ssh`, `snap`.
* **I would use this when:** I am logged in as the root user and need to configure user-specific settings or scripts that only root should access.

#### 4. `/etc`
* **What it contains:** Host-specific system-wide configuration files and startup scripts. It holds the "settings" of your Linux system.
* **Example files/folders:** `/etc/passwd`, `/etc/hostname`, `/etc/fstab`, `/etc/nginx/`.
* **I would use this when:** I need to change system settings, update network configurations, change the machine name, or edit service config files.

#### 5. `/var/log`
* **What it contains:** Dynamic data and system log files generated by the operating system and running services. Critical for debugging.
* **Example files/folders:** `/var/log/syslog`, `/var/log/auth.log`, `/var/log/nginx/`.
* **I would use this when:** An application crashes, a service fails to start, or I need to investigate unauthorized login attempts.

#### 6. `/tmp`
* **What it contains:** Temporary files created by the system and running applications. Files here are usually deleted automatically when the system reboots.
* **Example files/folders:** Session tokens, temporary socket files, installer caches.
* **I would use this when:** I need a temporary space to extract an archive file or run a one-time setup script without cluttering permanent storage.

---

### Additional Directories (Good to Know)

#### 1. `/bin`
* **What it contains:** Fundamental and essential command binaries (executable programs) required for the system to boot and run in single-user mode.
* **Example files/folders:** `ls`, `cp`, `mv`, `mkdir`, `bash`.
* **I would use this when:** The system is in repair mode and I need access to basic, foundational core commands.

#### 2. `/usr/bin`
* **What it contains:** The majority of executable commands and user applications used during normal system operation.
* **Example files/folders:** `git`, `python3`, `curl`, `wget`, `docker`.
* **I would use this when:** I install a new standard utility or package and want to check where its executable file lives.

#### 3. `/opt`
* **What it contains:** Optional or add-on third-party software packages that do not follow the standard Linux directory layout.
* **Example files/folders:** `/opt/google/chrome`, `/opt/aws/`, `/opt/containerd/`.
* **I would use this when:** I install proprietary or large standalone software suites that keep all their internal files grouped together in one folder.

---

### Hands-on Verification Commands
```bash
# Find the largest log file in /var/log
du -sh /var/log/* 2>/dev/null | sort -h | tail -5

# Look at a config file in /etc
cat /etc/hostname

# Check your home directory
ls -la ~
```

## Part 2: Scenario-Based Practice

### Scenario 1: Service Not Starting
**Question:** A web application service called `myapp` failed to start after a server reboot. What commands would you run to diagnose the issue? Write at least 4 commands in order.

* **Step 1:** `systemctl status myapp`
  * **Why:** To get an immediate high-level overview of the service state. This tells me if it is active, inactive, or crashed with an error code.
* **Step 2:** `journalctl -u myapp -n 50 --no-pager`
  * **Why:** To extract the actual application error logs and stack traces. This reveals why the code itself refused to start (e.g., missing database connection, bad configuration).
* **Step 3:** `systemctl is-enabled myapp`
  * **Why:** To verify if the service was ever configured to start automatically on system boot. If it returns `disabled`, it explains why it did not start after the reboot.
* **Step 4:** `tail -n 20 /var/log/syslog`
  * **Why:** To check system-wide errors if the application failed completely before `systemd` could even track its specific log context.

### Scenario 2: High CPU Usage
**Question:** Your manager reports that the application server is slow. You SSH into the server. What commands would you run to identify which process is using high CPU?

* **Command 1:** `top`
  * **Why:** Provides a real-time, dynamic view of active system processes. It automatically sorts processes by highest CPU usage percentage at the very top.
* **Command 2:** `ps aux --sort=-%cpu | head -10`
  * **Why:** Generates a static snapshot of the top 10 resource-heavy processes. This is perfect for capturing the exact Command, Owner, and PID (Process ID) to paste directly into an incident ticket.

---

### Scenario 3: Finding Service Logs
**Question:** A developer asks: "Where are the logs for the 'docker' service?" The service is managed by systemd. What commands would you use?

* **Command 1:** `systemctl status docker`
  * **Why:** This shows the status and includes the last few lines of active logs right at the bottom of the output.
* **Command 2:** `journalctl -u docker -n 50`
  * **Why:** Queries the central systemd journal database to display exactly the last 50 log entries specific to the Docker daemon process.
* **Command 3:** `journalctl -u docker -f`
  * **Why:** Streams the live, real-time log output directly to the screen. This allows the developer to watch how the service responds while they trigger actions.

---

### Scenario 4: File Permissions Issue
**Question:** A script at `/home/user/backup.sh` is not executing. When you run it: `./backup.sh`, you get: `"Permission denied"`. What commands would you use to fix this?

* **Step 1: Check current permissions**
  * **Command:** `ls -l /home/user/backup.sh`
  * **Why:** To inspect the user permission flags (e.g., `-rw-r--r--`). It confirms the complete absence of the `x` flag, which indicates the file is restricted from running as an executable program.
* **Step 2: Add execute permission**
  * **Command:** `chmod +x /home/user/backup.sh`
  * **Why:** This modifies the file permissions by adding the execute flag (`+x`) for the owner, allowing it to run as a script.
* **Step 3: Verify it worked**
  * **Command:** `ls -l /home/user/backup.sh`
  * **Why:** To check that the flags now display `-rwxr-xr-x` (often highlighted in green text in the terminal), confirming it is safely executable.
* **Step 4: Try running it**
  * **Command:** `./backup.sh`
  * **Why:** To execute the script now that the block has been lifted.
